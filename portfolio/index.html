02问题与目标

为什么不用现成方案

主流 RAG 方案默认依赖向量数据库与 Embedding 服务，部署门槛与运行成本高， 且中文效果高度依赖外部模型。我希望验证一个更朴素的假设： 在单一领域的知识库上，精心调校的词项检索能否达到可用水平？ 如果能，就得到一个零成本、可完全离线、行为可解释的基线。

三个可验证的目标

  1. 零第三方依赖：pip install 为空，任何有 Python 的机器都能跑
  2. 可量化的检索质量：自建标注集，给出 Recall / MRR 等标准指标
  3. 可抑制幻觉：资料不足时明确拒答，而不是强行编造

03系统架构

检索链路全部在本地完成，不产生任何网络请求；生成层是唯一的可选外部依赖，且具备离线降级路径。

分块策略

按 Markdown 标题维护标题栈，为每段正文生成 一级 › 二级 形式的 标题路径；再按空行切段、贪心装箱到 600 字符以内，相邻块保留 100 字符重叠窗口。 标题路径既是检索时的加权字段，也是回答时展示的引用位置。 围栏代码块内的 # 注释 会被识别并跳过，不参与标题解析。

检索评分

final = BM25(text) × (1 + 1.8 × 标题命中率 + 0.4 × 词项覆盖率)

IDF 采用 BM25+ 形式 ln(1 + (N−df+0.5)/(df+0.5))， 保证词项出现于过半文档时权重恒为正。标题命中率让「标题即答案」的 FAQ 片段优先浮出； 词项覆盖率抑制「单个高频词重复命中」压过「多词共同命中」。

04量化评测

评测集由 71 条手工标注查询组成，每条标注「问题 → 期望文档 → 正确片段中必须出现的特征串」； 脚本会先校验特征串确实存在于期望文档中，防止标注错误污染指标。 同时给出两档判定：文档级（召回对文档）与片段级（召回对具体段落）， 避免用宽松指标掩盖「找到了文档但没找到正确段落」的真实缺陷。 后处理管线（候选截断 30 → 单文档限流 3 → 近似去重 → Top-5）在四种方法间完全一致。

05一次由评测驱动的缺陷修复

这是整个项目里我认为最有价值的部分：不是「我做了一个 RAG」，而是 「我用评测发现自己做错了，并证明改对了」。

  1. 1
    建立评测基线

    构造 71 条标注查询（问题 → 期望文档 → 正确片段特征串）与 7 条领域外问题，同时实现 3 个对照方法，先用数据看清现状，而不是凭感觉判断好坏。

  2. 2
    暴露缺陷

    首次评测发现：检索指标尚可（Doc Recall@5 = 100%），但拒答准确率只有 28.6% —— 系统几乎不对领域外问题拒答，倾向于从无关片段里强行摘录，是典型幻觉来源。

  3. 3
    定位根因

    原拒答条件是「召回片段与问题无任何共享词项」。中文 bigram 分词下该条件几乎不可能成立：任意两句中文都会因「可以」「怎么」这类高频二元组产生重叠。改为构造查询内归一化特征：词表覆盖率与 IDF 覆盖率。

  4. 4
    二次修正

    第一版特征把「不在词表中的词项」排除在分母外，导致领域外查询分母趋近 0、比值反而被放大到 1.0 以上 —— 特征方向完全反了。修正为按「语料中最稀有词项」计权后，三项特征方向一致、分离清晰。

  5. 5
    标定与复测

    网格搜索阈值，发现 84 组解并列最优；改用 max-min 间隔准则二次筛选，把阈值推到特征分布空隙中央。最终拒答率 28.6% → 100.0%，误拒 0/71。

06关键技术决策

每个决策都写清问题、选择、代价与结果——取舍比结论更能说明工程判断力。

中文分词：bigram 而非词典分词

问题
jieba 等分词器会引入第三方依赖与词典文件，与「零依赖」目标冲突。
选择
不依赖词典，对连续汉字串做二元切分（n 个汉字生成 n−1 个 bigram）。这是信息检索领域的经典无词典方案，召回稳定。
代价
索引体积约为按词切分的 2~3 倍；中文同义词不做归一（「电脑」与「计算机」视为不同词项）；单字查询命中率低。
结果
在 12 篇语料上词项数 3991，索引 227.2 KB，仍在可接受范围。

IDF 采用 BM25+ 形式

问题
经典 Okapi BM25 的 IDF 在高文档频率下会取到负值，导致「出现于过半文档的词」反而拉低相关度得分。
选择
改用 ln(1 + (N−df+0.5)/(df+0.5))，保证任何词项的权重恒为正。
代价
与原始论文的数值不再严格可比，但对短文本与小语料更稳健。
结果
消融实验显示该形式下高频词不再产生负贡献，评分曲线单调可解释。

离线抽取式回答作为降级路径

问题
未配置大模型密钥时，系统不应直接不可用；但离线模式无法做推理。
选择
保留双模式：配置接口则走大模型，否则从召回片段中按词项加权重叠度抽取原句并附引用编号。
代价
抽取模式只摘录原句，不做推理、比较与数值换算，摘录内容可能来自相邻条目。
结果
保证「零配置也能跑通完整问答链路」，便于在无网络环境验证检索质量；输出中已明确标注该局限。

远程接口必须有密钥，本机地址可留空

问题
早期实现只检查 api_base 与 model 是否填写，导致默认配置每次都发起一次注定 401 的请求。
选择
用 ipaddress 解析主机名，判定是否为环回或私有地址：远程必须提供密钥，本机/内网地址允许留空。
代价
多了一层地址判定逻辑，非标准端口或域名映射的内网服务可能被误判。
结果
默认配置安静走离线模式；本地 Ollama / vLLM 无需密钥即可使用。

能力现状与原因

检索模型纯词项匹配，无向量语义检索。同义改写召回弱，是失败样例的主要来源

离线回答仅摘录原句，不做推理、比较或数值换算，需靠大模型补足
评测集由作者手工构造并自校验，规模 71 条；不能替代多人标注的公开基准

08复现方式

无第三方依赖，克隆后即可运行；评测脚本与网页生成脚本一并提供。

# 1. 建立索引（默认读取 ./docs）
python rag.py ingest

# 2. 提问：未配置密钥时自动使用离线抽取式回答，资料不足则拒答
python rag.py ask "如何导入已有笔记？"

# 3. 只看检索结果与得分
python rag.py search "导出支持哪些格式" -k 5

# 4. 端到端自检（2573 行代码，34 项断言）
python selftest.py

# 5. 复现本文全部评测数据与图表
python benchmark.py
python build_portfolio.py

配置大模型（可选）：设置 RAG_API_KEY 即可， RAG_API_BASE 与 RAG_MODEL 可指向任意 OpenAI 兼容服务，包括本地 Ollama。
