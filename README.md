# 小型 RAG（检索增强生成）

一个**零第三方依赖**的本地知识库问答程序。只用 Python 标准库实现了完整的
RAG 链路：文档解析 → 分块 → 倒排索引 → BM25 检索 → 大模型生成。

- **检索永远离线**：不联网、不上传、不需要密钥，开箱即用。
- **生成可选在线**：配置任意 OpenAI 兼容接口（DeepSeek / Moonshot / 通义 /
  本地 Ollama、vLLM 均可）即可获得综合式回答；不配置则自动降级为离线抽取式回答。
- **中文友好**：内置中英文混合分词（中文二元切分 + 英文复数归一），
  无需 jieba 等分词依赖。
- **自带浏览器界面**：`python rag_web.py` 即可，同样零依赖；页面上能看到引用来源
  与每一条召回片段的得分、命中词项、拒答特征。

## 快速开始

需要 Python 3.9 以上，无任何 pip 依赖。

```bash
# 1. 建立索引（默认读取 ./docs 目录）
python rag.py ingest

# 2. 提问（未配置密钥时自动使用离线抽取式回答）
python rag.py ask "如何导入已有笔记？"

# 3. 只看检索结果与得分，不生成回答
python rag.py search "导出支持哪些格式" -k 5

# 4. 浏览器界面（可选，需先建索引）
python rag_web.py --open
```

把你要问答的 `.md` / `.txt` 文档放进 `docs/` 目录，重新执行 `ingest` 即可。
也可以直接指定任意路径：

```bash
python rag.py ingest D:/我的资料 E:/项目文档/readme.md
```

## Web 界面（可选）

`rag_web.py` 用标准库 `http.server` 起一个只监听本机的问答页面，不需要任何
前端构建工具，也没有 pip 依赖：

```bash
python rag_web.py                 # http://127.0.0.1:8765
python rag_web.py --port 9000 --open
```

页面提供：提问输入、引用来源、以及一个可展开的**调试面板**（三条拒答特征与
阈值对照、每条召回片段的得分/命中词项/原文）。适合观察打分行为、验证拒答是否
按预期触发。

右上角「模型设置」可以在页面里直接填 API Key、测试连通性、切换在线/离线模式，
不必重启服务、也不用改环境变量。密钥**只存在进程内存**，不写磁盘、不回显、不记
日志，重启即失效；接口只回显末 4 位（如 `••••••••6789`）。

三条设计约束：

- **零第三方依赖**：只用 `http.server` / `json` / `threading` 等标准库。
- **检索链路仍然离线**：服务默认只绑定 `127.0.0.1`，不发起任何外网请求；
  只有配置了大模型时，生成环节才按与 CLI 完全相同的规则访问 `api_base`。
- **生成逻辑不复制**：Web 层直接复用 `cli._answer_once`。否则 Web 与 CLI 会各自
  演化出不同的拒答/回退行为，而这类漂移极难被发现。

> `--host 0.0.0.0` 会让同网段其他机器访问到你的知识库，也能改写模型配置。
> 默认不开，需要时自行承担。

接口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/` | 问答页面（`web/index.html`，单文件、无外部资源） |
| `GET` | `/api/meta` | 索引统计、文档清单、检索/拒答参数、大模型可用性（**不含密钥**） |
| `POST` | `/api/ask` | `{"question": str, "top_k": int?, "no_llm": bool?}` → 答案、引用、召回片段、拒答特征 |
| `GET` | `/api/llm` | 当前模型配置，密钥仅回显末 4 位 |
| `POST` | `/api/llm` | `{"api_base"?, "model"?, "api_key"?, "clear_key"?}` → 写入进程内存 |
| `POST` | `/api/llm/test` | 用当前配置发一次最小请求，返回 `ok` / `error` / `latency_ms` |


## 配置大模型（可选）

设置环境变量即可启用，无需修改代码：

```bash
# DeepSeek
export RAG_API_KEY=sk-xxxxxxxx
export RAG_API_BASE=https://api.deepseek.com/v1
export RAG_MODEL=deepseek-chat

# 本地 Ollama（本机地址允许不带密钥）
export RAG_API_BASE=http://localhost:11434/v1
export RAG_MODEL=qwen2.5:7b
```

Windows PowerShell：

```powershell
$env:RAG_API_KEY="sk-xxxxxxxx"
```

也可以复制 `config.example.json` 为 `config.json` 后填写。配置优先级：
**环境变量 > config.json > 内置默认值**。

> 判定规则：远程地址必须提供 `api_key`；`localhost` / `127.0.0.1` / 内网 IP
> 允许留空。因此默认配置（填了 `api_base` 但没填密钥）会安静地走离线模式，
> 不会每次都发起一次注定失败的请求。

## 换一份语料：菜谱知识库

引擎本身与语料解耦，换一份文档只需换配置。仓库附带 `config.cook.json`，把
[HowToCook](https://github.com/Anduin2017/HowToCook) 的菜谱接成第二个知识库：

```bash
# 语料不入库（data/ 已 gitignore，约 79 MB），先自行拉取
git clone https://github.com/Anduin2017/HowToCook data/C8/cook

python rag.py --config config.cook.json ingest          # 建独立索引 .rag_index_cook
python rag.py --config config.cook.json ask "红烧肉怎么做" --no-llm
python rag_web.py --config config.cook.json --port 8766 --open
```

实测规模：**372 篇菜谱 / 2083 个片段 / 32560 个词项 / 33.7 万字符**
（`dishes/template` 是写作模板而非菜谱，已通过 `exclude` 排除）。

**为什么单开一个知识库而不是并入 `docs/`**：`docs/` 的 12 篇文档承载着 143 条
标注查询的评测基线。把 373 篇菜谱混进去，检索结果会被菜谱淹没，所有指标失效。
两份语料、两个索引、两套配置，互不干扰——这也顺带验证了引擎没有硬编码任何
与「云雀笔记」相关的东西。

> **同义异形词：靠配置化查询扩展解决，而不是调阈值。** 菜谱语料里那道菜写作
> 「西红柿炒鸡蛋」，用户常问「番茄炒鸡蛋」。二元切分下 `番茄` 与 `西红` 毫无
> 重叠，最相关的文档进不了候选集，实测 `idf_cov=0.1653`（阈值 0.18）直接拒答。
> 放宽阈值不可行——那会让真正该拒答的领域外问题一并放行。改为在
> `config.cook.json` 的 `synonyms` 字段声明 `{原词: [别名, ...]}`，查询时把
> 别名**追加**到查询串末尾，由分词器重新切分（`西红柿` → `西红`/`红柿`）。
> 开启后同一问题 `idf_cov` 升到 0.3111，top-1 命中「西红柿炒鸡蛋」。
>
> 默认配置的 `synonyms` 为空，检索行为与未实现该功能前**完全一致**——
> 重跑评测后 `index` / `metrics` / `tiers` / `refusal*` 各 section 逐字段未变。
> 别名表是数据不是代码：换知识库就换表，不同语料互不干扰。

## 工作原理

```
文档(.md/.txt)
   │  loader     多编码读取（UTF-8 / GB18030 / Big5 自动识别）
   ▼
分块 chunker     按 Markdown 标题切分 → 按空行切段 → 贪心装箱 → 重叠窗口
   │             每块记录「标题路径」（如 常见问题 › 如何导入）
   ▼
索引 index       Okapi BM25 倒排索引，标题路径与正文合并索引
   │             JSON 持久化到 .rag_index/index.json
   ▼
检索 retriever   候选集截断 → 单文档限流 → 近似去重 → Top-K
   │
   ▼
拒答 abstain     词表覆盖 / IDF 覆盖 → 资料不足则直接拒答
   │
   ▼
生成 generator   ① 大模型（OpenAI 兼容）  ② 离线抽取式（兜底）
```

### 检索评分

```
final = BM25(text) × (1 + 1.8 × 标题命中率 + 0.4 × 词项覆盖率)
```

- `idf(t) = ln(1 + (N - df + 0.5) / (df + 0.5))` —— BM25+ 形式，
  保证词项出现于过半文档时权重仍为正，避免经典 BM25 的负分问题。
- **标题命中率**：命中的查询词中出现在标题路径里的比例（按 IDF 归一）。
  让"标题即答案"的 FAQ 片段优先浮出。
- **词项覆盖率**：命中的去重查询词占全部查询词的比例。缓解"单个高频词
  重复命中"压过"多词共同命中"。

### 中文分词为什么用 bigram

不引入 jieba 等词典分词器，改用二元切分（长度为 n 的汉字串生成 n-1 个
bigram）。这是信息检索领域的经典无词典方案：召回稳定、无需模型文件，
代价是索引体积约为按词切分的 2~3 倍 —— 对小型知识库完全可以接受。

**已知局限**：中文同义词不做归一（"电脑" 与 "计算机" 视为不同词项）；
单字查询（如只输入"税"）命中率偏低，建议输入两个以上汉字。

## 基准评测

```bash
python benchmark.py        # 输出 benchmark_report.json
python benchmark.py --check-labels   # 仅校验标注集与语料是否一致
python build_portfolio.py  # 由评测数据生成 portfolio/index.html
```

评测集为 143 条手工标注查询（问题 → 期望文档 → 正确片段特征串）+ 7 条领域外问题。
脚本会先校验每条标注的特征串确实存在于期望文档中，防止标注错误污染指标。
判定分两档：**文档级**（Doc Recall）与**片段级**（Passage Hit，要求同时命中
期望文档且包含特征串），避免用宽松指标掩盖「找到文档但没找对段落」的缺陷。

143 条按难度分四层，分层统计比单一总分更有诊断价值：

| 层级 | n | 构造方式 |
| --- | --- | --- |
| `basic` | 71 | 问法与文档用词高度重合，考察「能不能检索到」 |
| `paraphrase` | 24 | 问法刻意避开原文用词，考察词项扩展能力 |
| `detail` | 24 | 答案埋在具体数值 / 路径 / 协议名里，考察片段级定位精度 |
| `confusable` | 24 | 问法只给主题、答案散落在多篇同主题文档中，考察跨文档区分 |

在 12 篇文档 / 98 个片段 / 3991 个词项的语料上：

| 方法 | Doc Recall@1 | Passage Hit@1 | Passage Hit@5 | MRR@10 |
| --- | --- | --- | --- | --- |
| **本方案**（BM25 + 标题加权 + 覆盖率） | **0.839** | **0.769** | 0.923 | **0.891** |
| 纯 Okapi BM25 | 0.818 | 0.755 | 0.923 | 0.878 |
| TF-IDF 余弦 | 0.811 | 0.706 | 0.902 | 0.872 |
| 关键词命中计数 | 0.713 | 0.657 | 0.909 | 0.810 |

分层的本方案表现（误拒率按生产阈值计算，见下一节）：

| 层级 | Doc Recall@1 | Passage Hit@1 | Passage Hit@5 | 误拒率 |
| --- | --- | --- | --- | --- |
| `basic` | 0.887 | 0.803 | 0.986 | 0.0% |
| `paraphrase` | 0.500 | **0.333** | 0.583 | **58.3%** |
| `detail` | 0.917 | 0.917 | 1.000 | 8.3% |
| `confusable` | 0.958 | 0.958 | 1.000 | 4.2% |

结论有三条，都可以回到代码与报告核对：

1. **两项启发式加权的收益完全来自 `basic` 层**（+4.2pt），在 `paraphrase` 与
   `detail` 层为 0，在 `confusable` 层为 −4.2pt。`confusable` 层唯一的失分项是
   「团队版的版本历史能保留多久？」：标题加权把 team-collaboration 的「变更审计」
   段落推到了首位（其标题含「团队」二字），而正确答案在 pricing。也就是说，这两项
   加权本质是**在词项已经重叠的前提下做重排序**——它既弥补不了同义改写造成的词项
   缺失，还会在跨文档区分时放大标题词的误导。整体 Top-1 提升因此从上一版标注集
   （只含 `basic` 层）的 +4.2pt 收窄到 +2.1pt（文档级）/ +1.4pt（片段级）。
2. **在 Top-5 上与纯 BM25 完全打平**（0.923 vs 0.923）—— 加权的作用是重排序而非
   扩大召回，与设计意图一致。TF-IDF 余弦在文档级接近本方案（差 2.8pt），片段级
   明显落后（差 6.3pt）。两者在 TF 的进入方式上不同：BM25 有 TF 饱和（`k1` 参数）
   且长度归一化是部分归一化（`b=0.75`），而该基线中 TF 以 `f / 文档长度` 线性进入、
   再按余弦做完整范数归一化。具体是哪一项造成片段级差距，本项目未做进一步拆解，
   此处不作为结论。
3. **同义改写是这套方法的结构性短板**：`paraphrase` 层片段命中率仅 0.333，
   而 `detail` / `confusable` 层在 0.92 以上。这与倒排索引依赖字面匹配的机制一致
   —— 数字、协议名、路径这类**独一无二的词项**反而是 BM25 最擅长的。这也解释了
   为什么工业界要在 BM25 之上叠加向量召回。

**评测可复现性**：四个方法的排名都以 `chunk_id` 作为二级排序键显式打破并列。
整数计数类基线（`keyword`）并列极多，若只按分数排序，并列项的相对次序会继承
`acc` 的插入顺序，而插入顺序又取决于 `set(tokenize(query))` 的迭代顺序 —— 后者
受 `PYTHONHASHSEED` 随机化影响，于是同一份代码、同一份语料换一个进程就会跑出
不同指标。修复前实测 `keyword` 的 MRR@10 在 0.8380~0.8514 之间漂移、Top-3 文档
召回在 0.9577~0.9718 之间跳变；修复后在不同哈希种子下 `metrics` 子树逐字段一致。
（该缺陷只影响两个基线函数；生产检索路径 `ragcore/index.py` 的排序本就带
`(-score, chunk_id)` 二级键。）

性能：查询延迟 P50 0.09 ms / P95 0.25 ms；全量建索引 14 ms；
索引文件 227 KB（约为正文的 13.8 倍字符数比）；加载堆内存峰值 2.6 MB。
（耗时类数据随机器负载波动，仅作量级参考；上表指标类数据可复现。）

## 拒答机制与阈值标定

资料不足时系统直接拒答，而不是从无关片段强行摘录。判定基于三个**查询内归一化**
特征（BM25 的绝对分数不可跨查询比较，因此不能直接用分数阈值）：

| 特征 | 含义 | 领域内中位 | 领域外中位 |
| --- | --- | --- | --- |
| `vocab_cov` | 问题词项能在索引词表中找到的比例 | 0.600 | 0.083 |
| `idf_cov` | 最高分片段覆盖的查询词项权重占比 | 0.360 | 0.077 |
| `norm_score` | 最高分片段得分 ÷ 全部查询词项总权重 | 0.669 | 0.174 |

**关键细节**：词表外（OOV）词项必须计入分母，并按「语料中最稀有的词项」计权。
早期实现只把「存在于词表中的词项」计入分母，导致领域外查询的分母趋近于 0，
归一化比值反而被放大到 1.0 以上 —— 特征方向完全反了。

阈值由 `benchmark.py` 网格搜索确定，目标函数为平衡准确率（领域外拒答率与
领域内不误拒率的算术平均）。由于存在大量并列最优解，改用 **max-min 间隔**准则
二次筛选：取每个阈值到最近样本值的归一化距离，再取三项最小值，选最大者，
等价于把阈值推到特征分布空隙中央，对分布漂移最不敏感。

作为对照：未加拒答判定、仅靠原始分数阈值时，领域外拒答率只有 28.6%；引入三特征
判定后达到 100%。

标注集扩到 143 条后，网格搜索给出的最优工作点是 `vocab_cov ≥ 0.25`、
`idf_cov ≥ 0.12`、`norm_score ≥ 0.3`，但生产配置**刻意没有采用它**：

| 指标 | 生产阈值 0.32 / 0.18 / 0（禁用） | 网格最优 0.25 / 0.12 / 0.3 |
| --- | --- | --- |
| 领域外拒答准确率 | **100%**（7/7） | **100%**（7/7） |
| 领域内误拒率 | 11.9%（17/143） | 11.2%（16/143） |
| 平衡准确率 | 94.1% | 94.4% |

两条理由：一是差距只有 0.3pt，相当于 143 条里 1 条查询，属噪声量级；二是这组
最优解的 **max-min 间隔只有 0.001**（上一版标注集上是 0.007），说明阈值几乎贴在
某个样本值上，特征分布之间已经没有空隙可站——它不是一个稳健工作点，换一批数据
就会失效。在没有稳健工作点时调整线上参数，风险大于收益。`norm_score` 本次虽被
标定选中，但启用它等于给拒答多加一条失效路径，而收益只有 1 条查询，故仍保持禁用。

真正值得关注的是**误拒集中在哪一层**：

| 层级 | 误拒率 |
| --- | --- |
| `basic` | 0.0%（0/71） |
| `paraphrase` | **58.3%**（14/24） |
| `detail` | 8.3%（2/24） |
| `confusable` | 4.2%（1/24） |

`basic` 层零误拒说明现有阈值对「问法与文档用词重合」的正常提问是安全的；但
`paraphrase` 层有 58.3% 的正常问题被直接拒答 —— **这不是检索没找到，而是系统
在检索前就判定「资料不足」**。根因是拒答判定依赖查询词项在语料中的覆盖率，而
同义改写天然压低覆盖率。这不是调阈值能解决的：把阈值降到 0.25 只把误拒从 17 条
降到 16 条，因为两类问题的特征分布已经重叠。要真正解决，需要在词项覆盖率之外
引入语义层面的相似度（向量召回或同义词扩展）—— 这也是本项目明确不做、但已知的
结构性边界。

## 自检

```bash
python selftest.py            # 34 项断言：分词、分块、建库、检索、限流去重、
                              # 离线回答、代码块标题回归、持久化一致性，
                              # 以及 README 指标表与 benchmark_report.json 的一致性
python rag_web.py --selftest  # 67 项断言：起真实 HTTP 服务跑完整请求链路
```

第 8 节「文档与评测数据一致性」会逐项比对 README 指标表的四个方法行与
`benchmark_report.json`，改评测后忘了同步文档会直接让自检失败 —— 这条约定
此前只靠人工遵守，实测已漂移过（`keyword` 行曾长期停留在一次更早运行的残值上）。

`rag_web.py --selftest` 在 `127.0.0.1` 的临时端口上起一个真实服务，用
`urllib` 发真实请求，覆盖三层：**页面静态检查**（标签配对、无外部资源引用、
关键结构存在）、**接口契约**（领域内返回答案与引用、领域外触发拒答、`top_k`
生效、meta 不泄露密钥）、**错误处理**（空问题 / 非法 JSON / 参数越界 → 400，
方法不对 → 405，未知路径 → 404）。不依赖浏览器，也不需要联网。

> 页面自检不是走过场：它曾用 6 个注入错误做过反向验证（删闭合标签、引入 CDN
> 外链、删 `id`、改 `charset`、多加一个闭合标签），每一项都能被捕获。这类缺陷
> 浏览器往往仍能渲染，靠肉眼极难发现。


`build_portfolio.py` 内置对生成页面的结构自检（标签配对、外部资源引用）与
SVG 几何自检（坐标越界、NaN、文字溢出画布），未通过则拒绝写出文件。

## 软件测试套件

`selftest.py` 是**冒烟测试**：跑通链路、验证关键路径，几十行断言，改一行代码
就能立刻知道有没有把东西弄坏。它不承担"按软件测试标准组织"的职责——没有用例
编号、没有需求追溯、没有等价类/边界值的推导依据，也无法作为交付物评审。

`tests/` 是另一层，按工程标准组织：

```bash
python tests/run_tests.py                  # 全量 96 个用例，写出 tests/test_report.md
python tests/run_tests.py --junit          # 同时输出 JUnit XML，可直接喂 CI
python tests/run_tests.py --filter chunker # 只跑编号/标题/需求含该关键字的用例
python tests/run_tests.py --verify-harness # 只做框架反向验证
python tests/run_tests.py --list           # 列出全部用例
python tests/mutation_check.py             # 变异测试：注入缺陷，确认用例会变红
```

| 维度 | 规模 |
| --- | --- |
| 用例 | 96（单元 66 / 集成 18 / 系统 7 / 非功能 5） |
| 需求 | 74 条，覆盖率 100%（`tests/SPEC.md` 是唯一来源，用例通过 `req_id` 引用） |
| 设计方法 | 等价类 25 / 边界值 28 / 判定表 13 / 错误推测 18 / 回归 8 / 性能 4 |
| 耗时 | 约 50 秒（含 4 次 CLI 子进程、8 个真实 HTTP 服务实例） |

**三个关键设计**

1. **需求追溯是硬约束，不是文档装饰**。`SPEC.md` 里的需求表由 `run_tests.py`
   解析成追溯矩阵；用例引用了不存在的需求编号、或有需求没被任何用例覆盖，
   `TC-META-002` 会直接失败。文档与代码不会各说各话。
2. **框架自己也要被测**。`--verify-harness` 注入必然通过 / 必然失败 / 必然抛
   异常三种探针，确认执行器分别判为 PASS / FAIL / ERROR，并确认 `assert_raises`
   在"本该抛异常却没抛"时会报错。**一个永远输出 PASS 的框架比没有测试更危险**。
3. **用变异测试证明覆盖不是空的**。`mutation_check.py` 往产品代码注入 4 个已知
   缺陷（放宽拒答阈值、取消代码块围栏保护、取消 overlap 上限、取消图片语法
   预清洗），确认每个都被对应用例捕获，捕获率 4/4。

**测出来的两个真实问题**

- **系统级 HTTP 代理会劫持回环请求**。本机若设置了 `HTTP_PROXY` 且未豁免
  `localhost`，Python `urllib` 会把发往 `127.0.0.1` 的请求也交给代理，连接拒绝
  会被代理改写成 `HTTP 502`。这会让"本地 Ollama / vLLM"这条路静默失效——本机
  推理不需要密钥，配置看起来完全正确，报错却是 `upstream connect failed`。
  排查方式：`python -c "import urllib.request as u; print(u.proxies, u.proxy_bypass('127.0.0.1'))"`，
  必要时设 `no_proxy=127.0.0.1,localhost`。
- **两个拒答阈值存在冗余**。把 `vocab_cov` 阈值从 0.32 放宽到 0.02，领域外查询
  仍被 `idf_cov` 拦住——说明 `vocab_cov` 在现有语料上并非独立必要。这与
  「`norm_score` 阈值标定后退化为 0」是同一类现象，记录在案但不改动生产阈值
  （改动需重跑 143 条标注集重新标定）。

## 已知边界

| 能力 | 现状 |
| --- | --- |
| 文档格式 | 仅 `.md` / `.markdown` / `.txt`（PDF/Word 需自行转换） |
| 检索模型 | BM25 词项匹配，无向量语义检索，同义改写召回弱；可用的补救手段是配置 `synonyms` 同义词表（菜谱库已配 10 组），但别名仍需人工维护 |
| 错别字 | 词面匹配对错别字无免疫力。更麻烦的是**拒答判定也会被误导**：「番茄超鸡蛋怎么做」里 `怎么`/`么做` 在菜谱语料中 df 很低、IDF 很高，仅凭这两个疑问词就能把 `idf_cov` 抬过阈值，于是不拒答却返回完全无关的菜谱。当前行为是"宁可答错也不拒答"的失败方向，尚未修复 |
| 分块 | 按字符数切分，未按 token 计量，长表格可能被截断 |
| 增量更新 | 按文件 SHA-1 复用缓存，但索引整体重建（万级片段内无感） |
| 并发 | 单进程；索引为单文件 JSON，不支持并发写 |
| 离线回答 | 只摘录原句，不做推理、比较或数值换算 |
| Web 界面 | 无鉴权、无会话；默认仅绑定 `127.0.0.1`，定位是本机单人调试，未做并发压测。页面内填的 API Key 只存进程内存，重启即失效 |
| 本地模型 | 生成层走 `urllib` 的默认代理设置。若系统级 `HTTP_PROXY` 未豁免 `localhost`，发往 `127.0.0.1` 的请求会被代理转发，本地 Ollama / vLLM 会以 `HTTP 502 upstream connect failed` 失败。需设 `no_proxy=127.0.0.1,localhost` |
| 评测集 | 由作者手工构造并自校验，143 条领域内 + 7 条领域外；难度分层由作者主观划分，不能替代多人标注的公开基准 |

如需语义检索，可在 `retriever.py` 中并行加入向量召回后做分数融合
（RRF），`index.py` 的接口无需改动。
